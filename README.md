# IAM Gateway — نظام إدارة الهوية والوصول والمصادقة

### Identity and Access Management (IAM) and Authentication — مشروع تخرج

بوابة ويب متكاملة لمؤسسة عراقية افتراضية هي **«شركة الرافدين للحلول التقنية» — بغداد**. تدير البوابة **هويات الموظفين** (من يدخل وكيف يثبت هويته) و**صلاحياتهم** (ماذا يرى وماذا يفعل). وتحمي **بوابة موظفين حقيقية من 12 وحدة أعمال**: الإجازات، ملفات الموظفين، الرواتب، فواتير الموردين، المصروفات، العملاء، الصفقات، تذاكر الدعم، الأجهزة، الإعلانات، دليل الموظفين، ومكتبة المستندات.

| | |
|---|---|
| **الخادم** | Node.js 22 + Express 5 |
| **قاعدة البيانات** | SQLite عبر المحرّك المدمج في Node.js (`node:sqlite`) — 21 جدولاً |
| **الواجهة** | HTML5 + CSS3 + JavaScript (Vanilla، بدون أطر عمل) — عربية بالكامل من اليمين لليسار |
| **المصادقة** | كلمة مرور (bcrypt) + مصادقة ثنائية TOTP (RFC 6238) + رموز استرداد |
| **الجلسات** | JWT قصير العمر + Refresh Token دوّار في Cookie من نوع HttpOnly |
| **التفويض** | RBAC + نطاق البيانات + قواعد العمل + أمن على مستوى الحقل (55 صلاحية، 15 دوراً) |
| **البيانات التجريبية** | 23 موظفاً، 7 أقسام، 868 حدث تدقيق، 37 فاتورة، 80 قسيمة راتب، 43 طلب إجازة، 32 صفقة، 40 تذكرة، 51 جهازاً |
| **الاختبارات** | 31 اختباراً آلياً — جميعها ناجحة |
| **حجم الكود** | نحو 5,000 سطر (خادم + واجهة + اختبارات + بيانات) |

## 1. التشغيل خلال دقيقة

**المتطلب الوحيد:** Node.js بإصدار **22.13 أو أحدث** (تحميله من [nodejs.org](https://nodejs.org)). لا يحتاج المشروع تثبيت خادم قاعدة بيانات ولا أي برنامج آخر.

</div>

```bash
git clone https://github.com/blackangiliq/ameer_graduate_project.git
cd ameer_graduate_project
npm install
npm start
```

<div dir="rtl">

بعدها افتح المتصفح على **http://localhost:3000**.

عند **أول تشغيل** يكتشف الخادم أن قاعدة البيانات فارغة، فينشئ الملف `data/iam.db` ويملؤه تلقائياً بكل البيانات التجريبية (الموظفين، الأدوار، الرواتب، الفواتير، سجل التدقيق …). كما يولّد مفاتيح التشفير السرية عشوائياً في `data/secrets.json`. هذا المجلد مستثنى من Git.

| الأمر | الوظيفة |
|---|---|
| `npm start` | تشغيل الخادم على المنفذ 3000 |
| `npm run dev` | تشغيل مع إعادة تحميل تلقائية عند تعديل الكود |
| `npm run seed` | **حذف كل البيانات وإعادة إنشاء البيانات التجريبية** (مفيد قبل العرض) |
| `npm run totp` | طباعة رمز المصادقة الثنائية الحالي (6 أرقام) لحسابات MFA التجريبية، بديلاً عن تطبيق الهاتف |
| `npm test` | تشغيل الاختبارات الآلية الـ 31 على قاعدة بيانات مؤقتة منفصلة |

> **قبل العرض أمام المشرف:** نفّذ `npm run seed`. السبب أن حساب `abbas.alsudani` يُقفل لمدة 15 دقيقة فقط من لحظة إنشاء البيانات، وأن الطلبات المعلّقة قد تكون اعتُمدت أثناء التجربة.

## 3. التقنيات المستخدمة ولماذا

### 3.1 الخادم (Back-end)

| التقنية | الإصدار | الاستخدام في المشروع | لماذا اخترناها |
|---|---|---|---|
| **Node.js** | 22.x | بيئة تشغيل الخادم | لغة واحدة (JavaScript) للخادم والواجهة، وفيها وحدات مدمجة للتشفير وقاعدة البيانات والاختبار |
| **Express** | 5.3.0 | إطار الويب: المسارات، الـ Middleware، تقديم الملفات الثابتة | الأكثر انتشاراً وتوثيقاً، ونموذج الـ Middleware فيه يناسب فرض سياسات الأمان طبقةً فوق طبقة. الإصدار 5 يلتقط أخطاء الدوال غير المتزامنة تلقائياً |
| **node:sqlite** (مدمج) | Node 22 | الاتصال بقاعدة بيانات SQLite | لا يحتاج تثبيت مكتبة أصلية (native) ولا ترجمة، ويعمل على Windows وLinux وmacOS مباشرة |
| **SQLite** | 3 | قاعدة البيانات العلائقية | قاعدة علائقية حقيقية (معاملات، مفاتيح أجنبية، فهارس، قيود CHECK) في ملف واحد، فيُشغَّل المشروع عند المشرف بلا إعداد خادم |
| **bcryptjs** | 3.0.3 | تجزئة كلمات المرور (cost = 12) | المعيار الصناعي لتخزين كلمات المرور: بطيء عمداً ويضيف ملحاً لكل كلمة. نسخة JavaScript خالصة لا تحتاج ترجمة |
| **jsonwebtoken** | 9.0.3 | توقيع رموز الوصول JWT والتحقق منها (HS256) | تنفيذ موثوق لمعيار RFC 7519، ويفرض الخوارزمية والجهة المُصدِرة (issuer) عند التحقق |
| **helmet** | 8.3.0 | ترويسات أمان HTTP: CSP، X-Frame-Options، nosniff، HSTS … | يغلق فئة كاملة من هجمات المتصفح (XSS، Clickjacking، MIME sniffing) بإعداد واحد |

## 5. رحلة الطلب: كيف تعمل الـ Middleware

**الـ Middleware** دالة تعمل على الطلب **قبل** وصوله إلى معالج المسار. لكل دالة ثلاثة خيارات: أن تمرر الطلب للدالة التالية بـ `next()`، أو أن ترد على الطلب وتوقف السلسلة، أو أن تعدّل الطلب (مثلاً تضيف `req.user`). ترتيب الـ Middleware في `src/app.js` **قرار أمني**: الأرخص والأعم يأتي أولاً، والأدق في النهاية.

![مسار الطلب عبر الـ Middleware](docs/diagrams/12-middleware-pipeline.png)

### 5.1 الطبقة العامة (تُطبّق على كل طلب) — `src/app.js`

| # | الـ Middleware | ماذا يفعل | ماذا يحمي منه |
|---|---|---|---|
| 1 | `helmet(...)` | يضيف ترويسات الأمان لكل استجابة (انظر أدناه) | XSS، Clickjacking، MIME sniffing |
| 2 | `express.json({ limit: '50kb' })` | يقرأ جسم الطلب JSON ويرفض ما يتجاوز 50KB | حجب الخدمة بطلبات ضخمة |
| 3 | `cookieParser()` | يقرأ الـ Cookie `iam_refresh` | — |
| 4 | `Cache-Control: no-store` + `apiLimiter` | يمنع تخزين استجابات الـ API في الذاكرة المؤقتة، ويحد كل IP بـ 600 طلب كل 15 دقيقة | تسرّب البيانات من الذاكرة المؤقتة، والإغراق |
| 5 | `authLimiter` على `/login` و`/register` و`/mfa/verify` | 30 طلباً فقط كل 15 دقيقة لكل IP، ثم HTTP 429 | التخمين الآلي، رش كلمات المرور |

| 13 | معالج الأخطاء المركزي | يطبع الخطأ في سجل الخادم ويرد برسالة عامة 500 | كشف بنية النظام عبر Stack trace |

### 5.2 نقطة فرض السياسة — `src/middleware/auth.js`

#### ① `authenticate` — «من أنت؟»

ينفّذ ستة فحوص بالترتيب، وأي فشل يعني **401** فوراً (نسخة مختصرة من الكود):

</div>

```js
function authenticate(req, res, next) {
  // 1) هل يوجد رمز؟                          ← 401 NO_TOKEN
  const token = header.startsWith('Bearer ') ? header.slice(7) : null;
  // 2) هل التوقيع صحيح ولم ينتهِ؟ (HS256 + issuer)  ← 401 INVALID_TOKEN / TOKEN_EXPIRED
  payload = tokens.verifyAccessToken(token);
  // 3) هل الجلسة sid ما زالت فعّالة في قاعدة البيانات؟  ← 401 SESSION_REVOKED
  const session = tokens.getActiveSession(payload.sid);
  // 4) هل الحساب ما زال active؟               ← 401 ACCOUNT_INACTIVE
  // 5) تحميل الأدوار والصلاحيات من قاعدة البيانات الآن (وليس من الرمز)
  user.roles = rbac.getUserRoles(user.id);
  user.permissions = rbac.getUserPermissions(user.id);
  // 6) إتاحة الهوية لباقي السلسلة
  req.user = user; req.session = session; next();
}
```

<div dir="rtl">

**لماذا الفحصان 3 و5 مهمّان؟** رمز JWT لا يمكن إلغاؤه قبل انتهاء مدته (15 دقيقة). لذلك:
- فحص الجلسة يجعل تسجيل الخروج، وإنهاء الجلسة من المسؤول، وتعطيل الحساب، **تسري في الطلب التالي مباشرة**.
- قراءة الصلاحيات من القاعدة مع كل طلب تعني أن **سحب دور من موظف يسري فوراً**، ولا ينتظر انتهاء الرمز. هذا مُثبت باختبار آلي.

#### ② `requirePasswordChanged` — «هل كلمة مرورك مؤقتة؟»

إذا كان `must_change_password = 1` (حساب أنشأه المسؤول، أو أعاد الدعم الفني تعيين كلمة مروره) يرد بـ **403 `PASSWORD_CHANGE_REQUIRED`** على كل شيء. وعند استلام هذا الرمز تحوّل الواجهة المستخدم إلى صفحة تغيير كلمة المرور.

#### ③ `requirePermission(...perms)` و`requireAny(...perms)` — «هل يحق لك؟»

</div>

```js
function requirePermission(...needed) {
  return (req, res, next) => {
    const missing = needed.filter((p) => !req.user.permissions.includes(p));
    if (missing.length === 0) return next();               // يملك كل المطلوب
    audit.log(req, { action: 'access.denied', status: 'denied',
      targetId: `${req.method} ${req.baseUrl}${req.path}`, details: { required: needed, missing } });
    return res.status(403).json({ error: 'ليس لديك صلاحية لتنفيذ هذا الإجراء', code: 'FORBIDDEN', required: missing });
  };
}
```

<div dir="rtl">

- `requirePermission`: يجب أن يملك **كل** الصلاحيات المذكورة.
- `requireAny`: يكفي أن يملك **واحدة** منها. يُستخدم للصفحات متعددة النطاقات، مثل `requireAny('leave:read:own', 'leave:read:department', 'leave:read:all')`، ثم يضيّق المعالج البيانات حسب أوسع نطاق يملكه المستخدم.
- **الرفض الافتراضي (Default Deny):** إذا لم تثبت الصلاحية فالجواب رفض.
- **كل رفض يُسجّل** في سجل التدقيق مع الصلاحية الناقصة.

**مثال حقيقي:** الموظف `omar.alani` يطلب `GET /api/finance/invoices`:

### 6.1 تسجيل الدخول — `POST /api/auth/login` في `src/routes/auth.js`

| الخطوة | ما يحدث | لماذا بهذا الترتيب |
|---|---|---|
| 1 | `authLimiter`: هل تجاوز هذا الـ IP عدد 30 محاولة؟ | يُرفض الطلب قبل أي عمل مكلف |
| 2 | البحث عن المستخدم باسم المستخدم **أو** البريد (استعلام مُعدّ) | — |
| 3 | إن لم يوجد: تُنفّذ مقارنة bcrypt **وهمية** ثم تعود رسالة عامة 401 | زمن الاستجابة يتساوى، فلا يعرف المهاجم أي الأسماء موجودة (منع **User Enumeration**) |
| 4 | هل `locked_until` في المستقبل؟ ← 423 | **قبل** فحص كلمة المرور، حتى لا يستمر التخمين على حساب مقفل |

| 6 | خطأ: يزيد `failed_attempts`. عند الوصول إلى **5** يُقفل الحساب **15 دقيقة** ويُسجّل `auth.account_locked`. الرسالة تبقى عامة: «اسم المستخدم أو كلمة المرور غير صحيحة» | الحماية من التخمين |

| 8 | MFA مفعّلة؟ ← **لا تُنشأ جلسة**، بل يُعاد `challengeToken` صالح 5 دقائق | العامل الثاني يكون إلزامياً فعلاً |
| 9 | لا MFA: تصفير العداد، إنشاء جلسة، إصدار الرموز، تسجيل `auth.login` | — |

### 6.2 كلمات المرور — `src/services/password.js`

- **التجزئة:** `bcrypt` بكلفة **12**، أي 2¹² = 4096 جولة، مع ملح عشوائي لكل كلمة. شكل القيمة المخزنة: `$2b$12$<22 حرف ملح><31 حرف تجزئة>`. حتى مدير النظام لا يعرف كلمة مرور أي موظف.
- **سياسة كلمة المرور** (تُطبَّق في **الخادم**، والواجهة تعرض قائمة تحقق حيّة لتسهيل الإدخال فقط):
  - 10 أحرف على الأقل و128 حرفاً على الأكثر.
  - حرف صغير، وحرف كبير، ورقم، ورمز خاص.
  - ليست من قائمة كلمات المرور المسرّبة الشائعة (`password123`، `qwerty`، `iraq123`، `baghdad123` …).
  - لا تحتوي اسم المستخدم ولا الجزء الأول من البريد.
- **سجل كلمات المرور:** الجدول `password_history` يحفظ آخر **5** تجزئات، ولا يمكن إعادة استخدام أي منها.
- **تغيير كلمة المرور** (`POST /api/auth/change-password`) يتطلب كلمة المرور الحالية، ثم **يُنهي الجلسات على كل الأجهزة الأخرى**.
- **كلمة المرور المؤقتة** (عند الإنشاء من المسؤول أو إعادة التعيين): 14 حرفاً عشوائية بـ `crypto.randomInt` تستوفي السياسة، وتُعرض للمسؤول **مرة واحدة**.

### 6.3 المصادقة الثنائية TOTP — `src/services/totp.js` و`src/routes/mfa.js`

**الخوارزمية (RFC 6238)** كما في الكود:

</div>

```js
function hotp(secret, counter) {
  const buf = Buffer.alloc(8);
  buf.writeBigUInt64BE(BigInt(counter));                                // 1) العدّاد = floor(الوقت / 30)
  const hmac = crypto.createHmac('sha1', base32Decode(secret)).update(buf).digest();  // 2) HMAC-SHA1
  const offset = hmac[hmac.length - 1] & 0x0f;                          // 3) الاقتطاع الديناميكي
  const binary = ((hmac[offset] & 0x7f) << 24) | (hmac[offset + 1] << 16) | (hmac[offset + 2] << 8) | hmac[offset + 3];
  return String(binary % 10 ** 6).padStart(6, '0');                     // 4) آخر 6 أرقام
}
```

<div dir="rtl">

**الإعداد (Enrollment):**
1. `POST /api/mfa/setup`: يولّد سرّاً عشوائياً **160 بت**، ويخزّنه **مشفّراً بـ AES-256-GCM**، ويعيد رمز QR.
2. يمسح المستخدم الرمز بتطبيق الهاتف.
3. `POST /api/mfa/enable` مع أول رمز صحيح، وعندها **فقط** تُفعَّل MFA. هذا يضمن أن الهاتف مربوط فعلاً.
4. يولّد الخادم **8 رموز استرداد** تُعرض مرة واحدة، ويُخزَّن منها بصمات SHA-256 فقط، وكل رمز صالح **لمرة واحدة**.

**عند الدخول:** `POST /api/auth/mfa/verify` مع `challengeToken` والرمز:
- يُقبل الرمز السابق والحالي والتالي (نافذة ±30 ثانية لفرق ساعة الهاتف).
- المقارنة زمنية ثابتة (`timingSafeEqual`).
- الرموز الخاطئة **تُحتسب ضمن محاولات القفل** (5)، فلا يمكن تجربة المليون احتمال.
- `challengeToken` نوعه `mfa_challenge` ولا يُقبل في أي مسار آخر. هناك اختبار آلي يثبت ذلك.

**الإيقاف** (`POST /api/mfa/disable`) يتطلب كلمة المرور **و**رمزاً صالحاً معاً. **إعادة الضبط** من الدعم الفني تكون عند فقدان الهاتف.

## 7. الجلسات والرموز بالتفصيل

### 7.1 الرمزان

| | Access Token | Refresh Token |
|---|---|---|
| **النوع** | JWT موقّع HS256 | قيمة عشوائية 256 بت |
| **المدة** | 15 دقيقة | 7 أيام |
| **مكانه في المتصفح** | متغير في **الذاكرة** داخل `api.js` (ليس في localStorage) | Cookie: `HttpOnly; SameSite=Strict; Path=/api/auth` (+ `Secure` في الإنتاج) |
| **مكانه في الخادم** | لا يُخزَّن (يُتحقق من التوقيع) | **بصمة SHA-256** فقط في جدول `sessions` |
| **إلغاؤه** | عبر إلغاء الجلسة `sid` التي يشير إليها | مباشرة بـ `revoked_at` |
| **يُرسل مع** | كل طلب: `Authorization: Bearer ...` | `/api/auth/refresh` و`/logout` فقط |

**محتوى JWT حقيقي** بعد فك ترميزه (Base64URL). JWT **موقّع وليس مشفّراً**، لذلك لا يُوضع فيه أي سرّ:

</div>

```json
{ "alg": "HS256", "typ": "JWT" }
{ "sub": "15", "username": "omar.alani", "sid": "7021cb1e-222a-4645-ba1f-4666e9bc2c0b",
  "typ": "access", "iat": 1794389293, "exp": 1794390193, "iss": "iam-gateway" }
```

<div dir="rtl">

**لاحظ:** الصلاحيات **ليست** داخل الرمز، بل تُقرأ من القاعدة مع كل طلب.

### 7.2 التجديد الصامت والتدوير وكشف السرقة

![مخطط التتابع](docs/diagrams/06-auth-sequence.png)

- عندما ينتهي الـ Access Token ويرد الخادم بـ 401، يستدعي `api.js` تلقائياً `POST /api/auth/refresh`، ثم يعيد الطلب الأصلي دون أن يشعر المستخدم.
- **التدوير (Rotation):** كل استخدام لرمز التحديث يُصدر رمزاً **جديداً** ويُبطل القديم.
- **كشف إعادة الاستخدام:** إذا قُدّم رمز قديم (سبق تدويره)، فهذا يعني وجود نسختين: نسخة المستخدم ونسخة السارق. عندها **تُلغى الجلسة كلها** ويُسجَّل `auth.refresh_token_reuse`:

</div>

```js
// src/services/tokens.js
if (!safeEqual(session.refresh_token_hash, sha256(secret))) {
  revokeSession(session.id, 'refresh_token_reuse');   // رمز قديم ← سرقة ← إنهاء الجلسة
  return { error: 'reuse', session };
}
```

<div dir="rtl">

![دورة حياة الرمز](docs/diagrams/07-token-lifecycle.png)

### 7.3 متى تُلغى الجلسات؟

| الحدث | أي الجلسات | سبب الإلغاء المسجّل |
|---|---|---|
| تسجيل الخروج | الجلسة الحالية | `logout` |
| إنهاء الجلسة من «أجهزتي» | الجلسة المختارة | `user_revoked` |
| إنهاء من المسؤول (`sessions:revoke_any`) | الجلسة المختارة | `admin_revoked` |
| تغيير كلمة المرور | **كل الأجهزة الأخرى** | `password_changed` |
| إعادة تعيين كلمة المرور من الدعم الفني | كل الجلسات | `password_reset` |
| إعادة ضبط MFA | كل الجلسات | `mfa_reset` |
| تعليق الحساب أو تعطيله | كل الجلسات | `account_suspended` / `account_disabled` |
| إعادة استخدام رمز تحديث | الجلسة المعنية | `refresh_token_reuse` |

صفحة **«الجلسات النشطة»** تعرض لكل جلسة: الجهاز، وعنوان IP، وهل تم التحقق بـ MFA، ووقت البدء، وآخر نشاط، ووقت الانتهاء.

## 8. التفويض (Authorization): كيف يتم التحكم

### 8.1 النموذج

</div>

```
المستخدم ──(user_roles)──► الأدوار ──(role_permissions)──► الصلاحيات
   │                                                         │
   └──── الصلاحيات الفعلية = اتحاد صلاحيات كل أدواره ◄──────────┘
```

<div dir="rtl">

- **صيغة الصلاحية:** `مورد:إجراء` أو `مورد:إجراء:نطاق`. أمثلة: `users:create`، `invoices:approve`، `leave:read:department`.
- **كل مستخدم يملك دور `employee`** (الخدمة الذاتية) إضافة إلى دوره الوظيفي.
- **المستخدم الجديد** يحصل على `employee` فقط (**أقل الصلاحيات**).
- **55 صلاحية** موزعة على **15 دوراً**، وتظهر كاملة في صفحة «الأدوار والصلاحيات» على شكل مصفوفة.

![نموذج RBAC](docs/diagrams/08-rbac-model.png)

### 8.2 الطبقات الأربع للتفويض

صلاحية «الإجازات» وحدها لا تكفي، فالمؤسسة الحقيقية تقرر على أربعة مستويات:

| # | الطبقة | السؤال | مثال | الكود |
|---|---|---|---|---|
| ① | **الصلاحية (RBAC)** | هل يحق لك **الإجراء**؟ | المندوب لا يملك `invoices:read` فيُرفض | `requirePermission` |
| ② | **النطاق (Scope)** | **أي سجلات**؟ | `leave:read:own` / `:department` / `:all` | `resolveScope` + `scopeWhere` |
| ③ | **قاعدة العمل** | هل يحق لك **هذا السجل**؟ | لا تعتمد طلبك · المحاسب حتى 10 ملايين · المندوب يعدّل صفقته فقط | `leaveDecisionBlock` · `invoiceBlock` · `dealEdit` · `ticketActions` |
| ④ | **الحقل** | **أي أعمدة**؟ | الراتب و IBAN تتطلب `salary:read` | `shapeRecord` |

الطبقة الثالثة تجعل النموذج **هجيناً RBAC + ABAC**: القرار يعتمد على **خصائص السجل** (المبلغ، المالك، القسم، الحالة)، وليس على الدور فقط.

![تدفق التفويض](docs/diagrams/05-authorization-flowchart.png)

### 8.3 ② النطاق — داخل استعلام SQL نفسه

</div>

```js
// src/routes/apps/_helpers.js
const SCOPE_ORDER = ['all', 'department', 'own'];
function scopeOf(user, base) {                     // scopeOf(user, 'leave:read') → 'department'
  return SCOPE_ORDER.find((s) => can(user, `${base}:${s}`)) || null;
}
function scopeWhere(scope, user, userCol, deptCol) {
  if (scope === 'all') return { sql: '1 = 1', params: [] };
  if (scope === 'department') return { sql: `${deptCol} = ?`, params: [user.department_id] };
  return { sql: `${userCol} = ?`, params: [user.id] };
}
```

<div dir="rtl">

- الصفوف غير المسموحة **لا تُقرأ من القاعدة أصلاً**.
- إذا طلب الموظف `?scope=all` وهو لا يملكه، تعيد `resolveScope` نطاقه هو، بصمت.
- الواجهة تعرض تبويبات «بياناتي / قسمي / كل المؤسسة»، والتبويبات التي لا يملكها المستخدم تظهر **معطّلة**.

### 8.4 ③ قواعد العمل — مثال الفواتير

</div>

```js
// src/routes/apps/finance.js
function invoiceBlock(user, inv) {
  if (inv.status !== 'pending') return 'الفاتورة ليست قيد الانتظار';
  if (!can(user, 'invoices:approve')) return 'ليس لديك صلاحية الاعتماد';
  if (inv.created_by === user.id) return 'لا يمكنك اعتماد فاتورة سجّلتها بنفسك (من يُدخل لا يعتمد)';
  if (inv.amount > 10_000_000 && !can(user, 'invoices:approve_unlimited'))
    return 'المبلغ يتجاوز حد اعتمادك (10,000,000 د.ع) — يتطلب المدير المالي';
  return null;   // مسموح
}
```

<div dir="rtl">

**الدالة نفسها تُستخدم في موضعين:**
1. عند **عرض** القائمة، لحساب `_actions` (الأزرار) و`_note` (سبب المنع) لكل صف.

وبهذا ما تعرضه الواجهة مطابق دائماً لما يسمح به الخادم، ولا يمكن تجاوزه بتعديل الواجهة أو بتغيير رقم السجل في الرابط (**IDOR**).

### 8.6 قواعد منع تصعيد الصلاحيات (في إدارة الهوية)

- لا يمكن لأي مسؤول تعديل **أدواره** أو **حالة حسابه** بنفسه.
- فقط `super_admin` يمنح دور `super_admin` أو يعدّل حساب من يملكه.
- صلاحيات `super_admin` ثابتة لا تُعدّل من الواجهة، وأدوار النظام لا تُحذف.
- **فصل المهام:** `iam_admin` يُسند الأدوار لكنه لا يملك `roles:manage` لتعديل محتواها، و`security_auditor` يقرأ فقط.

### 8.7 الواجهة لا تقرر شيئاً

- القائمة الجانبية تُبنى من صلاحيات المستخدم (`layout.js`)، فالموظف لا يرى «سجل التدقيق» أصلاً. لكن هذا **تحسين للتجربة وليس أماناً**: لو كتب الرابط يدوياً تظهر صفحة 403، ويرفض **الخادم** طلب البيانات ويسجّل المحاولة.
- كل صفحة تعرض شريط **«الصلاحيات التي تحكم هذه الصفحة»**: ✓ أخضر لما يملكه المستخدم، و✗ مشطوب لما لا يملكه.
- الأزرار تأتي من `_actions` التي حسبها الخادم، وسبب المنع يظهر تحت الزر 🔒.

## 12. دورة حياة الهوية (Joiner – Mover – Leaver)

![دورة حياة الهوية](docs/diagrams/03-identity-lifecycle.png)

| المرحلة | كيف تتم | ماذا يضمن النظام |
|---|---|---|
| **Joiner — تسجيل ذاتي** | `/register` ← حالة `pending` + دور `employee` | لا دخول قبل موافقة `users:disable` |
| **Joiner — من المسؤول** | «+ مستخدم جديد» ← كلمة مرور مؤقتة تُعرض مرة واحدة | `must_change_password` يمنع أي استخدام قبل تغييرها |
| **Mover** | إسناد الأدوار بمربعات اختيار | يسري **فوراً** · يُسجَّل ما أُضيف وما حُذف |
| **قفل تلقائي** | 5 محاولات فاشلة | 15 دقيقة، أو فك فوري من `users:unlock` |
| **تعليق** | `suspended` مع سبب | إنهاء كل الجلسات |
| **Leaver** | `disabled` | إنهاء كل الجلسات · الحساب لا يُحذف (للتدقيق) · صفحة الأجهزة تكشف ما يجب استرجاعه · الصفقات والعملاء تظهر «موظف سابق» لإعادة الإسناد |

## 14. قاعدة البيانات

**21 جدولاً** في خمس مجموعات. كل الاستعلامات **Prepared Statements** بمعاملات `?`، وهذا يمنع حقن SQL. والعمليات المركّبة تتم داخل **معاملات** (Transactions).

| المجموعة | الجداول |
|---|---|
| **الهوية** | `departments` · `users` · `password_history` · `employee_profiles` |
| **المصادقة** | `sessions` · `mfa_recovery_codes` |
| **التفويض** | `roles` · `permissions` · `role_permissions` · `user_roles` |
| **المساءلة** | `audit_logs` |
| **المحتوى المحمي** | `announcements` · `leave_requests` · `payroll_runs` · `payslips` · `invoices` · `expense_claims` · `customers` · `deals` · `tickets` · `assets` · `resources` |

**كيف تُخزَّن القيم الحساسة؟**

| القيمة | التخزين | السبب |
|---|---|---|
| كلمة المرور | **bcrypt** (تجزئة بطيئة + ملح) | لا حاجة لاسترجاعها أبداً |
| سر TOTP | **AES-256-GCM** (تشفير مصادَق) | الخادم يحتاج قراءته لحساب الرمز |
| Refresh Token ورموز الاسترداد | **SHA-256** | قيم عشوائية طويلة لا تحتاج تجزئة بطيئة |
| مفتاحا JWT والتشفير | **خارج القاعدة**: متغيرات البيئة أو `data/secrets.json` | لو سُرّب ملف القاعدة وحده فلن يكفي المهاجم |

## 15. الواجهة الأمامية (Front-end)

| الملف | الدور |
|---|---|
| `public/js/api.js` | يحفظ Access Token **في متغير بالذاكرة فقط**. عند تحميل أي صفحة يستدعي `/refresh` ليحصل على رمز من الـ Cookie (**Silent Refresh**). عند 401 يجدد ويعيد الطلب مرة واحدة. ويحتوي `UI.esc()` الذي تمر عبره **كل** قيمة تُدرج في HTML لمنع XSS |

## 16. الضوابط الأمنية (OWASP / STRIDE)

| الخطر | الضابط في المشروع |
|---|---|
| **A01 Broken Access Control** | `requirePermission` على كل مسار · رفض افتراضي · نطاق داخل SQL · قواعد ملكية السجل ضد IDOR · حجب الحقول في الخادم · منع تصعيد الصلاحيات |
| **A02 Cryptographic Failures** | bcrypt · AES-256-GCM · SHA-256 · `crypto.randomBytes` · `timingSafeEqual` · الأسرار خارج الكود |
| **A03 Injection** | Prepared Statements في كل الاستعلامات · `UI.esc()` لكل المخرجات · CSP صارمة · حماية CSV من حقن الصيغ |
| **A04 Insecure Design** | MFA · قفل الحساب · تدوير الرموز · فصل المهام · Maker–Checker · حدود الاعتماد |
| **A05 Security Misconfiguration** | Helmet · إخفاء `X-Powered-By` · لا Stack trace للعميل · `Cache-Control: no-store` |
| **A07 Identification & Authentication Failures** | سياسة كلمات المرور · منع User Enumeration · Rate limit · انتهاء الجلسات · إلغاء الجلسات عند تغيير كلمة المرور |
| **A09 Logging & Monitoring Failures** | سجل تدقيق شامل غير قابل للحذف · لوحة مراقبة · تسجيل كل رفض مع سببه |
| **CSRF** | API يعتمد ترويسة `Authorization` · Cookie بخاصية `SameSite=Strict` ومحصور في `/api/auth` |
| **Clickjacking** | `frame-ancestors 'none'` + `X-Frame-Options` |
| **Open Redirect** | `?next=` يقبل المسار الداخلي فقط |

| STRIDE | التهديد | الضابط |
|---|---|---|
| **S**poofing | سرقة كلمة مرور | bcrypt + MFA + قفل + Rate limit |
| **T**ampering | تعديل JWT ليصبح `sub = 1` | توقيع HS256 + فرض `alg` و`iss` |
| **R**epudiation | «لم أعتمد هذه الفاتورة» | سجل تدقيق بالمنفّذ والوقت وIP |
| **I**nformation Disclosure | تسريب ملف القاعدة · رؤية الرواتب | تجزئة وتشفير · أمن على مستوى الحقل |
| **D**enial of Service | إغراق الدخول | Rate limit + حد حجم JSON |

## 20. الإعدادات ومتغيرات البيئة

كل الأرقام الأمنية في ملف واحد هو `src/config.js`. ويمكن تغيير بعضها بملف `.env` (انسخ `.env.example`):

| المتغير | القيمة الافتراضية | الوصف |
|---|---|---|
| `PORT` | `3000` | منفذ الخادم |
| `NODE_ENV` | `development` | عند `production` تُفعّل `Secure` للـ Cookie وHSTS |
| `JWT_SECRET` | يُولَّد عشوائياً (384 بت) | مفتاح توقيع JWT |
| `MFA_ENCRYPTION_KEY` | يُولَّد عشوائياً (256 بت) | مفتاح AES لتشفير أسرار TOTP |
| `ACCESS_TOKEN_TTL` | `900` ثانية (15 د) | مدة رمز الوصول |
| `REFRESH_TOKEN_TTL` | `604800` ثانية (7 أيام) | مدة الجلسة |
| `BCRYPT_COST` | `12` | كلفة التجزئة |
| `AUTH_RATE_LIMIT` | `30` | محاولات الدخول لكل IP كل 15 دقيقة |

ثوابت أخرى في `config.js`:
- **القفل:** 5 محاولات ← 15 دقيقة.
- **كلمة المرور:** 10 أحرف على الأقل، وسجل آخر 5.
- **MFA:** 6 أرقام كل 30 ثانية، بنافذة ±1، و8 رموز استرداد.
- **مهلة خطوة MFA:** 5 دقائق.
- **حد اعتماد المحاسب** في `finance.js`: 10,000,000 د.ع.
